iOS shake-to-undo probe

Open this on the iPhone that gets the alerts, with Settings → Accessibility → Touch → Shake to Undo on. Shake means a firm wrist flick, twice. Work down the sections in order and note which ones produce “Undo Typing”.

0. Baseline — nothing typed

Shake now, having touched nothing on this page.

Expected: no alert. If you get one, the undo queue survives page loads and none of the app-side fixes can help.

1. Native typing, field still focused

Type 3–4 digits, then shake without dismissing the keyboard.

Expected: “Undo Typing”. This is the ordinary case.

2. Native typing, blurred and removed

Type into the field above, tap the button (which blurs it and removes it from the DOM, exactly like the wizard tearing down a screen), then shake.

The key question. An alert here confirms the diagnosis: the undo queue is page-wide and outlives the field, which is why the HUD gets alerts with no text input anywhere on screen.

3. Script-applied typing (the fix)

Same keyboard, but every keystroke is applied by script with beforeinput cancelled — the shipped guard. Type, then shake (focused and after blurring).

Expected: no alert. If you get one, prevention is not enough on this iOS version.

4. Subframe teardown (the best-effort clear)

Redo section 1 or 2 to arm an alert, confirm you get one, then tap this and shake again. It mounts a throwaway iframe and drops it, which should make WebKit discard the page’s registered edit commands.

No alert after tapping = the clear works and is worth keeping. Alert anyway = drop dropNativeUndoHistory’s iframe half; prevention is doing all the work.
